## 当前实现范围（2026-09-14）

## 1. 方案结论

系统划分为“通用追踪模块”和“4S 店展车分析模块”，共享同一套追踪技术，通过稳定、版本化的接口协作。展车分析是系统内可独立启停、开发、测试和升级的业务模块，不将平面图、展车、客户会话和报表规则写入追踪算法或原工作台。

核心做法是：人工上传平面图及展车、摄像头等配置，通用追踪服务持续输出不含 4S 店业务语义的人员观察记录；展车分析模块独立完成空间映射、看车事件和统计，每个门店每天形成一份包含当日数据的报告。两个模块分别拥有自己的配置与数据，前端在同一个系统入口下分别展示。追踪不必结束，就能持续更新当日草稿；已保存日志在保留期内可供复核和重算。

第一版采用单店内网部署、人工标注展车位置、临时到店会话编号。特征向量仅保存在追踪进程内存中，不写数据库、文件、日志或快照；特征数据库扩展留到后续。展车模块的配置、轨迹事件、消费进度和日报仍须保存，建议业务数据使用自身 SQLite，报告使用 HTML 加 JSON 数据附件。业务数据库不保存特征向量。

一期主要交付链路是“人工配置、复用追踪、展车分析、每日一报”。不默认引入永久客户身份库、向量数据库或大模型逐帧分析。特征内存模式意味着追踪进程重启后身份可能重新分配；已有当日数据可继续汇总，但不能保证重启前后同一人的自动去重。

追踪算法只有一份实现，不为展车模块复制或分叉模型、跟踪器和 ReID。兼容升级后的追踪服务会向原工作台和展车模块提供改进后的结果，展车业务逻辑无需重复移植算法。改进效果仍须现场回归验证，不等于每次模型更换都会自动提高业务准确率。

系统回答“访客在哪辆车附近停留、停留多久、是否再次返回”，输出可解释的关注线索。位置接近或停留较久，不等于真实购买意愿，也不能直接推导购买概率。

## 2. 业务目标、范围与前提

### 2.1 第一版目标

- 门店人员：在平面图上查看访客动线及当前停留状态。
- 单次到店：查看访问过的展车、顺序、有效停留时长、回访次数和可复核依据。
- 单辆展车：查看去重到访人数、有效访问人数、停留时长分布、回访率和时间趋势。
- 门店运营：比较不同展车的关注情况，辅助安排接待、调整展车布局。
- 每日交付：按门店当地日期生成一份日报，覆盖当日所有可用数据、展车指标、访客访问明细及质量说明；日内可查看尚未结束的草稿。
- 运维：判断数据是否完整、哪些摄像头离线、哪些时段的统计不可靠。

这里的“回访”指同一次到店内再次返回同一辆展车，不是跨天识别回头客。“访客人数”按个体会话统计，不等于购车家庭数或销售线索数。

### 2.2 第一版不包含

- 人脸识别、实名识别、默认跨天或跨门店身份关联。
- 通过外观推断年龄、收入、职业等个人属性。
- 自动识别全部车型配置或 VIN。
- 仅凭人员框自动断言注视方向、开门、试坐、咨询或成交。
- 未经验证的“购买意向百分比”和自动销售决策。
- 特征向量落库、落盘快照、重启后历史特征恢复；本期只保留未来扩展边界。
- 在未知硬件、网络条件下承诺任意路数、零丢帧或固定识别准确率。

试坐、开门、后备厢查看等行为识别，以及经授权的业务系统关联，作为独立后续需求评估。

### 2.3 尚待确认的现场条件

- 摄像头数量、位置、视角、分辨率、帧率、码率、协议及录像能力。
- 平面图比例尺、主要通道、展台高差、反光区域、遮挡及盲区。
- 展车数量、换位频率，以及车辆编号与车型的维护责任人。
- 服务器 CPU、GPU、显存、内存、磁盘与网络条件。
- 是否必须每帧推理、允许的实时延迟、故障恢复时间和数据损失窗口。
- 员工与访客如何区分、访问权限、告知及授权要求、数据保留期限。

以下设计按“固定摄像头、展车相对固定、单店单服务器试点”展开。门店路数、硬件采购与最终工期须在现场勘查及压测后确定。

| 能力 | 当前项目情况 | 本方案新增内容 |

| 在线日志 | 每个任务持续写 `tracks.jsonl`，含人员框、ID、读取时间等 | 帧级空结果、心跳、断流、版本、去重键、可靠分段及消费进度 |

| 特征保存 | 主要在任务内存中；全局特征无按时间清理机制 | 保持仅内存，完善容量和生命周期边界；数据库存储及身份恢复延后 |
| 在线展示 | 原画与模型标注分开，存在推理队列溢出跳帧策略 | 增加端到端指标、数据缺口说明和业务看板 |
| 调度 | 同时只允许一个任务；离线任务内部支持有界并行 | 在线常驻优先；一期离线错峰，后续再做资源隔离 |
| 重启 | 未完成任务被标记失败，不自动续跑 | 可恢复配置与日志统计；新追踪运行重新建身份，日报说明跨运行去重限制 |
| 安全 | 同源及 Host 边界，无登录和角色权限 | 认证、授权、审计、视频源白名单、保留和删除策略 |

源码核对位置：`web/pipeline.py::run_online`、`web/jobs.py::JobManager`、`global_identity.py::GlobalIDManager`、`torch_detector.py::UltralyticsYOLOPersonDetector`、`web/app.py`。

当前的 30 分钟清理针对不活跃的局部轨迹状态，并不删除全局特征库。当前日志刷新使用 `flush()`，并非已实现断电持久化。摄像头在请求中的数组编号也不能直接充当永久摄像头编号。

## 4. 系统组成与部署方式

### 4.1 责任边界与单向依赖

| 模块 | 自己负责 | 不得承担或直接访问 |
| --- | --- | --- |
| 通用追踪核心 | 检测、单镜头跟踪、ReID、跨镜头身份关联、通用质量控制 | 不识别门店、车型、看车区域、客户会话和兴趣分数；不依赖展车代码 |
| 通用追踪服务 | 在线/离线任务、采集、媒体、结果协议、日志、内存特征与通用生命周期策略 | 本期不持久化特征；不写展车数据库，不执行访问时长、回访和日报规则 |
| 轻量协议与客户端 | 数据结构、版本、验证、事件读取与任务客户端 | 不包含模型实例、共享可变跟踪器、GPU 依赖或业务规则 |
| 原追踪工作台 | 原在线/离线配置、追踪预览和结果下载 | 不被强制要求配置门店或安装展车模块 |
| 展车分析模块 | 门店及平面图、展车、业务角色、到店会话、停留和回访、报表及独立存储 | 不复制追踪算法，不导入追踪私有实现，不读写其数据库或内存对象 |
| 系统入口与通用基础设施 | 导航、认证、反向代理、服务注册和受限健康汇总 | 不承载追踪算法或展车规则，不成为混合业务逻辑的新大文件 |

允许的依赖是：追踪服务使用追踪核心和协议；两个工作台及展车消费者使用公开协议或客户端。追踪核心及服务不能反向导入展车模块，展车模块也不能直接调用 `web.pipeline`、`CameraTracker` 或 `GlobalIDManager` 的内部方法。

展车规则只能读取追踪观察并产生自己的业务结果，不能在分析过程中直接修改 GID。需要算法级空间约束时，另行增加通用、可选、版本化的约束接口；不能引入专用于 4S 店的算法分支。

### 4.2 运行隔离与任务共享

一期采用同一仓库管理、同一服务器部署、独立服务进程运行的方式。通用追踪服务继续支持原工作台；展车 API 和统计进程可独立启动、停止、重启和部署。同一域名下由入口代理到不同服务，不要求一开始建设多机微服务平台。

同一追踪任务的结果可同时供原工作台和展车模块使用：通过任务 ID 绑定和独立消费游标共享，不重复拉取视频、加载模型或重新推理。多消费者不能从同一个破坏性队列竞争取走记录；一个消费者确认进度不能删除其他消费者尚未读取的数据。

任务所有权和订阅分开：关闭展车页面、停止统计或解除订阅，不停止共享追踪任务。停止自己创建且无人共享的追踪任务，也须通过明确的授权操作。共享任务的配置变更、取消和身份清理不能由任一订阅方隐式触发。

展车消费者停机时，追踪继续输出并在批准期限内保留日志，恢复后补算。展车数据库失败、迁移失败或规则异常不能使追踪进程退出。队列、日志和数据库有独立容量限制；耗尽时公开记录积压或缺口，不无界阻塞追踪或静默声称统计完整。同机磁盘、CPU 和内存仍是共享故障点，必须设置资源配额与告警，不能将进程隔离宣传为绝对故障隔离。

第一版保留单个在线追踪任务。展车分析消费该任务，不占用第二个推理任务名额；离线推理仍错峰。若需同时运行多个推理任务，再升级通用调度能力，不在展车模块自行启动另一套隐藏推理服务。

视频源位于授权内网，摄像头或 NVR 独立录像。分别检查 API、模型、摄像头和统计就绪情况，不能只以 HTTP 可访问作为整个系统健康依据。[FastAPI 部署说明](https://fastapi.tiangolo.com/deployment/concepts/)

### 4.3 代码、页面和依赖组织

以下为目标职责划分，不代表已创建这些目录；实施时优先使用薄适配层渐进整理，不一次性搬动所有历史文件。

| 目标目录/边界 | 内容 |
| --- | --- |
| `contracts/tracking/` | 轻量追踪事件、能力及控制协议，兼容性样本 |
| `tracking/core/` | 唯一的追踪算法实现；现有算法逐步归入此职责 |
| `tracking/service/` | 通用任务、采集、媒体、日志和内存特征；保留未来存储适配边界，对外公开 API |
| `tracking/client/` | HTTP/事件/只读日志适配器，不加载模型 |
| `modules/showroom/` | 独立 API、消费者、空间计算、业务规则、存储、迁移与配置 |
| `modules/showroom/static/` | 展车模块自己的页面、脚本、样式和状态 |
| `web/` | 原工作台与兼容入口；迁移时保持原路径和功能可用 |
| `tests/contracts/`、`tests/showroom/` | 协议兼容及展车独立测试；原追踪测试继续保留 |

系统导航提供“通用追踪”和“展车分析”两个入口。原工作台保留在线/离线功能；展车页面有自己的在线分析视图，可通过公开媒体接口复用视频组件。不得向原 `web/static/app.js` 和全局样式持续添加大量展车条件分支；共享组件必须不含车型和门店业务状态。

展车关闭时，不导入展车模块、不执行其数据库迁移、不加载其前端资源，不要求其配置存在。展车可只用轻量运行依赖和固定日志样本进行开发测试，无需下载 YOLO/TransReID 权重或安装 GPU 环境。

各服务可以使用 `APIRouter` 整理自己的接口，但路由分文件只解决代码组织，不等于独立进程或故障隔离；两类边界都需要落实。[FastAPI 多文件组织说明](https://fastapi.tiangolo.com/tutorial/bigger-applications/)

### 4.4 稳定集成接口

追踪协议只包含通用数据：运行和摄像头标识、通用 `scope_id`、时间、像素框、身份、质量、空帧、缺口和修订。`store_id`、`visit_id`、`vehicle_id`、布局及标定版本由展车模块在消费时补充，不能要求追踪核心生成这些字段。

一期数据通道采用追踪服务发布的版本化日志段和清单，展车通过只读 `TrackingEventSource` 适配器读取并独立保存游标。只读挂载限于已授权的结果目录，不暴露特征库、凭据和任务内部文件。将来换成事件 API 或消息系统，只替换客户端适配器，不改看车规则。

控制通道采用公开任务接口或 `TrackingClient`：查询、创建、绑定任务、读取状态、申请授权范围内的通用身份策略。底层原接口通过追踪侧适配器保持兼容，展车不直接访问原 `JobManager` 的内存或数据库。展车门店配置只保存稳定源引用，实际流凭据由追踪服务保管。

事件协议明确空值、像素坐标范围、时间来源、顺序、重复和身份修订语义；不得传模型类、NumPy 对象、可变跟踪器或依赖进程内引用的对象。协议、生产者和模型版本分别记录，支持升级、兼容读取与回滚。

### 4.5 追踪优化如何传递给展车分析

1. 原工作台和展车模块始终复用同一个已发布的追踪服务/实现，不各自复制模型推理代码。
2. 检测漏检、ID 切换、ReID 或推理速度改进，只修改追踪侧；在协议语义兼容时，展车侧继续读取同样结构，直接使用更新后的观察结果。
3. 停留阈值、展车布局、回访定义和报表优化，只修改展车侧；用固定追踪日志重放即可验证，不重跑模型。
4. 新追踪版本先用固定视频和业务样本回归，记录模型、阈值、协议、规则版本；验证后切换服务。算法更新可能改变结果分布，必须检查业务精确率、时长误差和历史可比性，不能理解为无验证自动更新。
5. 单纯重算旧日志只能改善业务规则结果，不能修复旧检测漏检。需要让历史数据获得新追踪能力时，须有保留期内的原视频、明确补算任务和新版结果，不能静默覆盖旧报表。

协议新增可选字段须规定默认值和未知字段处理；未知必需能力或事件类型不得默默忽略。破坏字段语义、时间或身份解释的变更提升主版本，并提供适配器或并行兼容窗口。版本化采用明确公共接口及兼容性原则，但不能仅凭版本号认定行为完全兼容。[语义化版本规范](https://semver.org/)

### 4.6 可验证的解耦约束

- 禁用或移除展车模块后，原在线、离线、预览、取消和下载测试仍通过。
- 无模型权重、无 GPU 的环境，仅凭协议样本可以运行展车规则和存储测试。
- 展车崩溃、数据库锁住或重放积压时，通用追踪和原视频工作台继续工作，资源上限和告警生效。
- 两个消费者读取同一运行各自得到完整记录；关闭其中一个不终止任务，也不改变另一个的进度。
- 对追踪与展车设置导入边界检查，禁止跨模块私有调用和跨库 SQL；数据库迁移分别测试。
- 新旧协议兼容样本及身份修订回放通过；协议不兼容时明确拒绝或使用适配器，不输出看似正常的错误统计。
- 每次追踪升级同时运行算法回归与展车集成测试，每次展车升级用固定日志做业务回归。协议兼容可以避免同步改代码，但质量验证不能省略。

## 5. 平面图、展车与时间标定

### 5.1 门店配置

展车模块为每个门店建立稳定 `store_id`，并维护门店到追踪服务 `scope_id`、稳定 `camera_id` 和运行的授权绑定。追踪服务只认识通用作用域和摄像头，不需要知道门店、车型或到店业务。摄像头密码由追踪服务通过受保护的配置读取，展车模块只持有源引用，不获取明文密码。

平面图设置原点、方向、单位和比例尺；地面坐标以米表示。支持配置车身占地多边形、看车区域、通道、入口、休息区和排除区。展车使用内部 `vehicle_id`，与展位、车型分别管理。

车辆换位或换车时创建新的 `layout_version` 并记录生效时间。旧日志按当时生效的布局解释，不能用今天的车位重算昨天并悄悄改变车型归属。相机移动或变焦后同样生成新标定版本，重新验收。

人工配置流程：

1. 上传平面图。一期优先支持 PNG/JPEG，限制文件大小和解码尺寸并检查真实文件类型；PDF/CAD 可先由用户导出图片，不要求一期开发自动 CAD 解析。
2. 设置平面图比例尺、门店时区及营业时段；圈定展车占地区域、看车区域、通道和排除区，录入车辆编号与车型。
3. 选择已授权摄像头，提供画面与平面图对应点，完成标定预览和误差检查。只上传一张平面图并不能自动完成视频坐标对齐。
4. 检查重叠区域、缺少字段、错误坐标和重复车辆编号，确认后发布配置版本及生效时间。配置文件可使用版本化 JSON 导入/导出，表单编辑同样可用。
5. 绑定追踪任务并开启展车分析。换车、移车、挪动摄像头时更新相应配置，不修改通用追踪代码。

上传的原图、标注和配置版本归展车模块管理，不进入追踪模型或特征内存。未完成标定或缺少展车映射的时段只能报告未配置、无法归属，不能自动猜测车辆；后补配置若要解释历史数据，必须明确其历史适用时间并产生报告修订。

### 5.2 视频位置映射

固定摄像头先检查镜头畸变；用地面对应点求视频到平面图的变换，使用分布在有效区域内的多个控制点，并留出独立检查点验证误差。平面单应性适用于同一地面平面；有台阶或展台时分区标定，不将不同高度强行套入同一变换。[OpenCV 单应性说明](https://docs.opencv.org/4.x/d9/dab/tutorial_homography.html)

人员位置优先使用可见脚部落地点；一期可将完整人员框底边中点作为近似，但必须记录质量。脚部被车挡住、人员框截断或目标位于标定范围外时，降低置信度或置为未知，不把身体框中心、车顶中心当成地面位置。

车身区域之外建立人工校准的看车区域，避开主要通道。人员离哪辆车最近仅作为候选条件，最终还要结合区域、停留、可见性和区域重叠程度。两个展车无法区分时保留候选和“归属不确定”。

### 5.3 跨镜头时间与空间一致性

统一使用 UTC 记录时间，界面按门店时区展示。优先使用可验证的源时间；同时保存接收时间、时间来源和同步误差。源 PTS 必须有可靠起点映射才能视为墙上时钟，不能直接跨摄像头比较。

当前在线代码使用本机读取时间，含网络与解码差异；离线视频各自从零开始。实施时需补时间偏移配置、摄像头时钟校验和重连后的时钟跳变处理。无法对齐的录像不能按“第几帧相同”认定同时发生。

同一时段的多镜头观察按可靠时间窗口合并；位置兼容时选择质量更高的观察或融合。位置明显冲突、跨镜头移动时间不合理时，标记身份冲突而非直接平均位置。缺少覆盖的路段不生成虚构轨迹。

## 6. 持续日志与增量处理

### 6.1 新日志协议

保留现有日志作为兼容输出或使用适配器读取；由追踪模块新增带 `schema_version` 的通用事件日志，不能把新字段视为当前接口已支持。旧日志缺少心跳、空帧或时间质量时，适配器必须声明能力缺失，不能凭空补成“完整观测”。

建议按帧输出人员数组，包括 `observations: []` 的空帧，另有连接状态和心跳记录。主要字段如下：

| 字段组 | 建议字段 | 用途 |
| --- | --- | --- |
| 唯一标识 | `record_id, scope_id, run_id, camera_id, stream_epoch, seq` | 重启、重连及重放后仍能去重；不含门店业务标识 |
| 时间 | `source_timestamp, received_at, event_time, timestamp_source, time_uncertainty_ms` | 区分源时间、接收时间与分析时间 |
| 类型 | `record_type` | 帧观察、心跳、断流、缺口、身份修订、追踪配置变更 |
| 观察 | `local_id, global_id, bbox, feature_quality, observation_quality` | 临时身份可为空；特征质量不是身份正确概率 |
| 版本 | `schema_version, producer_version, model_version, tracking_config_version` | 通用协议、生产者、模型和追踪参数可追溯 |
| 完整性 | 解码计数、推理计数、溢出计数、状态、缺失范围 | 区分无人、漏处理、断流和统计延迟 |

`run_id` 是一次追踪运行；`stream_epoch` 标记流重建或序号重置。`record_id` 在生成后固定，重试不换号。普通轨迹日志不包含特征向量和流地址密码。`store_id`、`visit_id`、`vehicle_id`、`calibration_version`、`layout_version` 和 `rule_version` 只进入展车模块派生记录，不回写追踪原始日志。

### 6.2 写入与持久化

1. 追踪将不可变记录提交给其自己的有界写入队列，由通用日志写入器写文件；不在推理循环中调用展车函数。限制记录数量和字节总量。
2. 按小时或文件大小切分日志段；文件名含运行和段编号。活动段与已封存段区分，不复用旧路径覆盖已有数据。
3. 批量刷新和同步文件，维护已持久化的段编号、字节偏移及序号；业务统计只提交到该持久化位置以内。
4. 封存时完成同步，保存清单和校验信息；统计跟随清单消费，避免切换文件遗漏或重复。
5. 日志写入失败、队列持续高水位或磁盘不足时告警；达不到可靠记录条件时暂停相关分析并标记缺口，原画及 NVR 尽可能继续工作。不能承诺有限缓存能够承受无限故障。

建议试点以不超过 1 秒的批量同步周期为起点，压测后调整。Python `flush()` 只解决语言层缓冲，强制同步文件还需要 `fsync()` 等机制；实际断电损失窗口受排队、系统和硬件影响，必须故障测试确认，不能直接把同步周期当作损失保证。[Python 文件同步说明](https://docs.python.org/3/library/os.html#os.fsync)

### 6.3 增量消费、去重与续算

- 统计程序只读新增完整记录，不定时从头扫描整个文件。文件尾部的半行等待补齐；封存后仍损坏的记录隔离并告警，不能静默略过。
- 每个消费者在自己拥有的数据库内记录日志段和字节偏移。展车消费者将去重标识、事件更新、统计状态和消费进度放在展车数据库的同一个事务中提交，不跨追踪数据库开启事务。
- 采用“可重复投递、幂等更新”：崩溃后允许重读，但同一记录不能重复增加时长或人数。去重键至少保留到其日志不再允许重放。
- 对跨摄像头短时乱序设置可配置等待窗口；过迟记录进入修订流程，重算受影响的访问区间并增加版本，不直接再累加一次。
- 全局 ID 后续纠正时追加身份映射修订记录。可重算保留期内受影响的事件，保存依据和审计信息；不能假定第一次分配的 GID 永远正确。
- 在线统计和离线补算使用相同规则及版本。离线校验默认写独立结果，经过确认再发布修订，不混入实时统计造成双计数。

后台可每 1–5 秒更新聚合状态，前端可每 5 秒刷新；这些是试点建议，不是当前已达到的性能指标。每份结果带数据截止时间、延迟、完整性和规则版本。

## 7. 看车事件与统计口径

### 7.1 会话与人员角色

在本次到店内建立临时 `visit_id`，并保存其与 `(run_id, global_id)` 的关系。新任务中的 GID 数值即使相同，也不代表同一访客。

未确认的 `global_id = null` 不能合并成一个访客。先按运行、摄像头和局部轨迹保存待定观察，确认后在允许窗口内补算；到期仍未确认则报告未关联数量，不强行计入去重访客数。

入口、出口有可靠覆盖时辅助会话开始和结束；否则按不活跃超时结束，标明“推断结束”，不能声称识别到了实际离店。无法判断是不是同一次到店时，不强行连接。第一版不主动识别跨日回头客；零点仍有连续可靠观察的同次访问按日期切分时长，不为出日报强制重启追踪。

内存特征随追踪进程退出而丢失。新运行必须有新的 `run_id`，不能按相同 GID 数字与旧访客自动合并。日报可合并各运行已记录的事件，但人员数须标为“已关联会话数/分段去重数”，列出重启次数和可能重复计数的边界；没有身份断点且通过验证时才称当日跟踪去重人数。

人员角色采用访客、员工、未知三态。员工通过经授权的标记或可靠业务机制排除，保留修正记录；仅凭穿着或停留久不能作为最终员工判断。角色不明时显示“人员统计”或未知数量，不把所有人员包装成已确认客户。

### 7.2 事件状态与有效时长

事件区分候选进入、有效停留、短暂失联、已离开、归属不确定。为区域边界设置进入和退出缓冲，避免检测框抖动产生大量假回访。

有效时长按相邻可靠观察的时间差累计，必须满足：同一访客、同一展车、时间单调、间隔在允许范围内、区域归属可信、期间无已知断流或盲区冲突。超过间隔上限的整段不计；不要仅截断为一个较小值后继续算停留。正常采样之间的区间估算应带上采样覆盖说明。

已知遮挡和缺失时间单独记录。短时失联可保持一次访问事件不被拆开，但缺失时间不因此自动进入有效时长；长时间未知则结束当前有效区间。

同一访客在重叠摄像头中的有效时间区间取并集，不能相加。同一时间无法区分相邻车辆时，保留未知，不把整段时间同时算给两辆车。

### 7.3 试点参数起点

以下仅供现场校准，不是行业标准、最终业务规则或现有代码默认值。

| 参数 | 试点起点 | 说明 |
| --- | --- | --- |
| 有效停留阈值 | 10 秒 | 达标后计入该事件此前已确认的有效区间；短于阈值记录为短暂停留，不断言无兴趣 |
| 相邻观察最大间隔 | 2 秒 | 按实际推理频率调整；若经常超限，应解决覆盖或算力问题，不盲目放宽 |
| 短失联事件衔接窗口 | 3 秒 | 只维持事件连续性，不自动计算丢失时间 |
| 回访离开间隔 | 15 秒 | 需有可靠离开证据，恢复检测不能直接算回访 |
| 会话不活跃结束 | 30 分钟 | 是新业务参数，不等于现有局部轨迹清理逻辑；受营业日和现场验证约束 |

看车区域大小按每辆车的实际通道和可站立空间标注，不统一画一个固定半径圆。

### 7.4 报表指标

- 到访人数：统计周期内进入展车区域的去重 `visit_id` 数，同时显示员工排除和未知角色数量。
- 有效访问人数：至少有一次达到停留阈值的去重访客数。
- 有效停留时长：可靠归属于该车的时间区间总长度；可按事件或访客展示，明确分母。
- 停留分布：报告中位数、分位数和样本量，避免少数长停留掩盖多数短访问。
- 同次到店回访率：有两次及以上有效访问该车的访客数，除以至少一次有效访问的访客数；分母为零时显示无数据。
- 展车访问顺序：先访问 A 再访问 B 的会话数量；表示观察到的访问顺序，不表示销售转化。
- 覆盖质量：可用视频时间、未知归属占比、时钟质量、漏处理与断流情况。

跨展车比较应同时展示可观测营业时长、区域客流和布局版本，不能仅按累计停留时间评价车型受欢迎程度。日报按门店时区的自然日统计，营业时段作为单独筛选和覆盖质量依据，不直接按 UTC 日期或日志文件日期切报表。具体切日、跨日访问和去重口径见第 9.3 节。

一期优先展示原始指标及排序依据。如需要综合关注度分数，先通过人工标注验证，再定义可解释、可版本化的规则；分数不解释为购买概率。

## 8. 内存特征、业务保存与后续扩展

### 8.1 存储选择

V1.2 将 V1.1 的特征数据库建设延后，但保持数据所有权解耦。一期明确区分三类数据：

- 追踪特征：只在追踪进程的内存容器中保存，停止或重启后释放，不建立特征数据库或特征文件。
- 通用追踪结果：不含向量的结构化日志、运行元数据、日志清单及必要源配置，保存在追踪模块管理的目录中；密码仍使用受保护配置。
- 展车业务结果：人工上传的平面图、标注、门店配置、访问事件、消费进度和报告元数据，归展车模块所有。建议使用 `MTMC_DATA_DIR/showroom/showroom.sqlite3` 保存事务数据，报告和原图放在该模块独立文件目录。

“特征仅内存”不等于“所有数据仅内存”。若当日轨迹事件和报告也不保存，进程退出后就无法可靠形成当天日报。因此本期保留业务持久化，但禁止在业务库、日志或附件中夹带向量、特征缓存快照。

展车不得读写追踪内部目录、配置或内存，只读已授权发布的结果。展车数据库和报表的锁、迁移或清理不应影响追踪。未来新增追踪特征数据库时也由追踪模块独立拥有，不与展车库合并，不允许跨模块 SQL。

展车数据库内部串行化写事务，读查询独立进行；跨模块控制使用请求 ID、幂等处理、状态查询和重试。展车侧在本地事务中记录待发送命令，追踪确认后再更新完成状态；本期不需要跨库分布式事务。

启用 WAL 并不意味着可以无限并发写；仍需控制写入竞争、长事务及 WAL 大小。重要业务提交采用合适的同步策略，不能误认为较低同步级别具有同样的断电持久性。数据库不直接放在多机共享网络文件系统上。[SQLite WAL 说明](https://www.sqlite.org/wal.html)

通用原始日志按作用域、运行和日期分段保存在追踪数据目录，展车模块只读授权的公开日志段；其派生事件保存在展车数据目录。视频由独立录像系统或受控文件存储保存，数据库只保存必要索引。源码、模型权重、运行数据和备份分开管理。

### 8.2 建议实体

| 所属模块 | 实体 | 主要内容 |
| --- | --- | --- |
| 追踪 | `sources / scopes / runs` | 稳定视频源、凭据引用、身份作用域、运行与参数 |
| 追踪内存 | `identities / feature_gallery` | 本期仅内存的通用身份及代表特征，不建立数据库表或落盘快照 |
| 追踪 | `log_segments / tracking_health` | 公开日志清单、持久化位置和通用运行健康状态 |
| 展车 | `stores / tracking_bindings / store_cameras` | 门店、授权任务绑定、源引用和安装位置；不保存流密码 |
| 展车 | `calibrations / layouts / vehicle_placements` | 标定、布局、生效时间、展车位置和看车区域 |
| 展车 | `visits / identity_bindings` | 临时到店会话、追踪身份引用及修订版本；无特征向量 |
| 展车 | `vehicle_visits` | 展车访问事件、有效区间、未知时长、证据范围和规则版本 |
| 展车 | `consumer_offsets / processed_records / analyzer_state` | 同事务提交的进度、去重键和分析状态 |
| 展车 | `data_gaps / command_outbox` | 业务覆盖缺口、待发送的授权控制及清理命令 |
| 展车 | `vehicle_aggregates / reports / report_jobs` | 按日期的聚合、报告版本、生成进度与补发状态，不含特征 |
| 各自拥有 | `audit_events` | 各模块各自记录配置、访问、修正、导出和删除审计 |

表中实体是职责模型，不代表全部使用数据库表。展车业务查询按门店、事件时间、车辆、会话建立索引；追踪内存按通用作用域及身份查找。存储隔离不等于授权隔离，API 仍需逐项检查权限。

### 8.3 一期内存模式与后续数据库扩展

- 特征的抽取、筛选、匹配和内存管理全部由追踪模块实现。保留代表样本而非无界累计每帧特征，设置每身份样本上限、作用域容量和可配置清理策略。
- 一期只使用内存实现；不为实现重启恢复偷偷增加序列化文件、数据库字段或快照任务。向量、模型对象和跟踪器状态不写进展车报告。
- 追踪进程重启后重新加载模型并建立新身份，历史日志不能恢复向量。展车统计进程单独重启不会清空仍在运行的追踪进程内存，可从保存的消费进度继续。
- 展车保存的是历史事件和身份引用，不是重新识别能力。可以汇总重启前后的已保存数据，但不自动连接不同运行的真实人员身份。
- 追踪内部预留 `FeatureStore` 等存储边界，一期使用内存实现；后续数据库实现仅替换追踪侧适配器，展车协议和业务规则保持不变。

后续扩展时再设计向量类型与维度、模型和预处理版本、期限、加密、快照一致性及启动加载。特征库由追踪模块拥有，恢复后仍需新观察确认，不能恢复旧本地轨迹或位置占用。扩展启用前已经丢失的内存特征无法凭空补回；重识别历史数据需要获准保留的视频重新推理。

“营业日结束”“客户离店”由展车模块判断，再通过有权限的通用身份策略接口申请过期或释放；追踪内部只处理作用域、身份和到期时间，不导入门店规则。共享任务不得由展车消费者擅自删除其他用途仍在使用的身份：绑定时确认任务所有权、授权范围和统一保留策略，不满足隔离要求则拒绝绑定或由用户明确建立独立任务。

### 8.4 保留与删除

下面是待门店确认的试点起点，不是法定期限或默认授权。

| 数据 | 建议试点策略 | 边界 |
| --- | --- | --- |
| 访客特征 | 一期仅内存，按任务生命周期、容量及通用过期策略清理 | 进程退出即丢失；不建特征文件或数据库，不以生成日报为由复制特征 |
| 原始轨迹日志 | 7 天 | 用于复核和重算；缩短前检查消费者已处理且符合业务要求 |
| 访问明细 | 30 天 | 不含姓名手机号，但仍视为需保护的可关联行为数据 |
| 日报明细、HTML/JSON 报告包 | 30 天 | 若包含临时访客访问明细，沿用明细保留期限；不能冒充匿名统计延长保存 |
| 仅按展车、日期汇总的统计 | 90 天 | 去除会话关联，避免把可追踪个人的明细误称匿名统计 |
| 录像、证据片段 | 由门店另行确认 | 最小必要保留；未接入录像时不得显示虚假的回放入口 |

到期清理由各模块分别执行并覆盖自己拥有的内存、业务数据库、日志、导出、备份及证据索引。本期特征无落盘备份可恢复。跨模块清理通过幂等请求和确认状态协作，未确认时不能报告全部删除成功。业务数据库行删除不等于磁盘上立即不可恢复，应结合磁盘加密、备份生命周期及存储清理策略。恢复旧业务备份后先应用已到期和已撤销规则，不能重新发布应删除的明细和报告。

消费者严重积压时，不能无限延长已经批准的保留期限。到期前告警；若仍无法消费，按批准策略清理并记录无法补算的区间，报表必须保留完整性缺口。

采用一致性在线备份并进行恢复演练，不简单复制正在使用的单个数据库文件作为完整备份。[SQLite 在线备份说明](https://www.sqlite.org/backup.html)

## 9. 前端与接口设计

### 9.1 页面

- 门店配置：上传平面图、控制点标定、展车及区域编辑、版本发布、生效时间、摄像头健康状态。
- 展车在线页：在独立页面复用追踪服务公开的视频接口，展示平面图人员位置、展车停留状态、更新延迟、未知区域和断流提示；原追踪工作台不增加门店必填配置。
- 访客详情：单次到店访问顺序、有效停留、回访、身份修订和证据时间段；默认临时编号。
- 展车分析：按时间段、展车或车型查看去重人数、停留分布、回访率和覆盖质量。
- 日报中心：按门店和日期查看当日草稿、历史日报、生成状态和修订记录，支持重新生成与下载；同时展示数据截止时间、异常时段、身份断点和日志积压。

证据回放需要单独接入 NVR 或录像索引，验证访问权限和时间偏移。当前在线追踪日志本身不是可播放的视频。

### 9.2 新接口草案

以下接口均为展车模块拟新增，统一放在 `/api/showroom/v1/` 命名空间，具体请求结构在实施阶段确定。原追踪 API 保留并由通用客户端适配；门店绑定只保存在展车模块，不给现有追踪请求模型塞入门店、车型、布局字段。

| 接口 | 用途 |

| `GET/POST /api/showroom/v1/stores` | 门店查询与配置 |
| `POST /api/showroom/v1/stores/{store_id}/floorplans` | 人工上传平面图，返回本模块资源编号；不自动替代标定 |
| `GET/POST /api/showroom/v1/stores/{store_id}/cameras` | 绑定已授权的追踪视频源与安装位置，不保存流密码 |
| `POST /api/showroom/v1/stores/{store_id}/tracking-bindings` | 绑定可用追踪任务并建立独立消费进度，不重复加载模型 |
| `POST /api/showroom/v1/stores/{store_id}/calibrations` | 保存并验证标定版本 |
| `POST /api/showroom/v1/stores/{store_id}/layouts` | 发布展车与区域布局版本 |

接口应支持门店授权、时间范围限制、分页和版本查询。前端不直接读取日志文件或数据库；实时推送可在轮询方案通过验收后增加。展车业务 API 和静态资源采用独立应用入口，系统导航或反向代理负责整合，禁用展车模块后原追踪路径仍可用。

### 9.3 每日一份报告

#### 9.3.1 日期范围和唯一性

每个门店、每个当地日期有一份逻辑日报，唯一键为 `(store_id, report_date)`；HTML 和 JSON 是同一份报告的不同呈现，不是两套独立统计。修订使用同一报告标识并递增版本，界面默认展示最新已发布版本，保留必要修订依据。

一期默认门店时区为 `Asia/Shanghai`，允许配置。日期 D 的统计区间为当地 `D 00:00:00` 到 `D+1 00:00:00`，左闭右开。例如 9 月 13 日日报统计 9 月 13 日的数据，生成时间可以是 9 月 14 日。营业时间单独展示，不将“生成当天”“最近 24 小时”和“报告日期”混为一谈。

使用带时区的时间处理和明确的事件时间；不要通过 UTC 字符串截取前十位归档本地日报。Python 可使用 `zoneinfo` 处理 IANA 时区；部署时验证所需时区数据可用。[Python 时区说明](https://docs.python.org/3/library/zoneinfo.html)

跨零点的有效停留区间在日界处切分，每日只累计落在自己范围内的部分。日内有效访问人数按“至少一次访问在当天的有效时长达到阈值”的访客计算，避免将多次短暂路过累加为一次有效访问；当日访问次数和回访次数以当天确认的进入/回访事件时间归属，前日延续访问另列“跨日延续”，不伪造一次新进入。小时趋势也按区间交集计算，不能把整段停留全部记到开始那一小时。

#### 9.3.2 报告必须包含的当日数据

| 报告部分 | 内容与口径 |
| --- | --- |
| 基本信息 | 门店、报告日期、时区、统计区间、营业时段、生成时间、数据截止时间、报告版本和状态 |
| 当日总览 | 观测到的去重会话数或分段去重数、员工/未知角色数量、有效访问会话数、当日有效停留总量；明确非实名真实人数 |
| 全部展车明细 | 当日展示过的每辆车及车型、有效展示时段、到访及有效访问人数、进入/回访次数、停留时长和分布、未知归属说明；不只列 Top 排名 |
| 小时趋势 | 每小时会话量、展车访问和有效停留，标注缺失或未监控时段，不将无数据补零 |
| 单次到店访问明细 | 临时访客编号、所属运行、当日在各车区的进入/离开、有效时长、访问顺序及回访；无足够证据时不填实际离店时间 |
| 平面图与区域统计 | 使用当日生效的平面图和展车布局，展示区域停留分布；统计热度按时间加权，不以检测框数量代替停留 |
| 关注线索 | 基于停留和回访的展车关注排序，说明规则和样本量，不输出未经验证的购买概率 |
| 数据质量 | 各路有效观测时段、断流、未配置/未标定区、未知归属比例、推理缺口、重启和身份断点、可能重复计数说明 |
| 追溯信息 | 正式输入运行及日志范围、模型与协议版本、规则版本、标定和布局版本、修订原因；有录像授权时提供证据索引 |

“包括当日数据”指覆盖该门店当天所有获准纳入的正式输入及其有效统计，不仅截取生成报告前的最后几分钟，也不只挑选最受关注的车辆。没有进入正式统计的测试、校验和重复补算任务不得直接混入报告。原始逐帧日志作为可追溯来源保留，不要求把所有日志行塞进阅读报告；JSON 附件保存报告指标和当日访问明细，不包含特征向量。

门店总人数对当日会话集合去重，不能将各车到访人数相加。人员未可靠区分时显示人员/未知数据，不称为已确认客户。追踪进程重启后，无法关联的会话按运行分别统计并醒目标注，不能合并 GID 数字或声称全天精确去重。

当日有配置变更时，按生效时间分段分析，报告展示各版本摘要或分段平面图，不能用收店时的布局覆盖整天。未完成配置的历史时段保留未知，人工补配后才可按明确适用范围生成修订。

#### 9.3.3 生成时机、补发与修订

1. 日内持续处理新日志，按需查看“截至当前”的草稿；当天尚未结束时不能把草稿标为完整日报。
2. 在展车服务内部配置按日生成任务。建议次日当地时间 00:10 生成前一日报告，预留晚到数据窗口；这个时间可配置，是拟实现的系统功能，本方案不会创建外部提醒或自动化。
3. 生成时检查截至日界的日志消费进度和各路观测状态。等待窗口过后仍有缺口，生成带“不完整/待补算”标记的报告，不能无限等待或假称完整。
4. 展车服务停机错过生成时间，启动后扫描保留期内缺失日期并补发。即使未全天运行，也形成该日“部分时段/无有效数据”报告，明确覆盖范围。
5. 定时触发、人工生成和重试使用同一报告键及幂等任务，不能因重复执行产生多份互相矛盾的正式日报。晚到数据、身份修订或规则更新触发新版本，不静默改动旧版数字。
6. 从一致的数据快照计算 HTML 和 JSON，保存数据截止位置、输入范围及版本。两种输出先写入临时版本目录，校验成功后再原子发布索引；数据库提交和文件发布之间的中断通过状态机重试恢复，不假定文件和数据库能共同原子提交。

数据库内的报告记录、任务状态和统计更新使用事务；原子事务能力不应外推为文件和数据库的跨介质原子性。[SQLite 原子提交说明](https://www.sqlite.org/atomiccommit.html)

#### 9.3.4 格式、保存与零数据

一期采用可在浏览器打开的 HTML 主报告，图表和必要图片使用自包含或随报告打包的本地资源，不依赖外部 CDN；同时提供同版本 JSON 数据供程序对接。后续如需 PDF 或其他格式，由独立报告渲染器扩展，不改追踪或看车规则。

建议保存在展车模块的数据目录，例如 `MTMC_DATA_DIR/showroom/reports/<store_id>/<YYYY-MM-DD>/<revision>/`，提供 `report.html`、`report.json` 和发布清单。具体目录、权限、保留期限和清理都由展车模块管理，未经授权不能作为公共静态资源暴露。

全时段摄像头健康、配置有效且没有观察到目标，可以显示“有效观测范围内为零”。全天未启动、未配置、断流或无法分析，应显示“无有效数据”，不能声称当天没有客户。部分时段有数据则输出已知指标和缺口，不补造其余时段。

报告若包含临时访客明细或路径，按明细权限和期限保护；标准导出不含脸部裁剪、姓名、手机号或特征向量。所有人工车型名、备注等输出应做转义，防止上传内容变成报告脚本。

#### 9.3.5 总结说明

先由确定性程序计算数字，再用模板生成文字结论，不依赖大模型才能出日报。可选大模型后续仅接收获准使用的聚合指标和质量说明，不读取特征，不猜测盲区，不替代人数和时长计算。

输出区分“观测事实、规则推断、运营建议”。示例（以下数据虚构，仅说明表达方式）：

> 9 月 13 日，访客 V023 在 A 车附近有效停留 6 分钟，形成 3 次有效访问，其中 2 次为当日回访；在 B 车附近有效停留 40 秒。另有 25 秒位置不可确认，未计入车辆停留。系统于 14:20 重启，此前和此后的身份无法自动关联，全天人数采用分段去重口径。本结果提供看车关注线索，不代表购买意愿结论。

## 10. 流畅性、容量与故障设计

### 10.1 三条独立验收口径

- 原始录像完整性：由摄像头或 NVR 链路检查录制时段、帧数或源序号、断流和存储状态。
- 前端播放流畅性：统计显示帧率、端到端延迟、客户端丢弃与网络异常。
- 推理覆盖率：按每路已解码且应处理的帧，核对实际完成推理的帧及缺失原因。不能把该比率误称为“相对摄像头全部源帧”的覆盖率。

当前在线队列有界，溢出时会丢弃旧帧。若业务要求每帧分析，必须修改相应策略并验证峰值算力与持续积压，不通过无限加大队列解决。算力不够时，应增加资源或明确降低输入规格；未经确认不偷偷抽帧。独立录像允许事后补算已成功录到的片段，但不能补回源头就没有记录的视频，也不能消除实时延迟。

### 10.2 容量估算方法

先采集代表性高峰片段，再以实际部署版本压测，不凭摄像头路数选择显卡型号。

日志日容量可按 `每秒记录数 × 平均记录字节数 × 运行秒数` 估算，帧级记录需要计入每帧人员数量；另加索引、备份与安全余量。录像容量按实际总码率和录制时长测算。特征容量至少考虑 `有效身份数 × 每身份样本数 × 向量维度 × 数据类型字节数`，另计索引和算法状态。

监控每路解码及推理速率、队列字节数与最老记录年龄、持久化延迟、消费延迟、GPU/内存/磁盘占用、有效身份数。定义告警与容量上限，不能只展示一个全局平均 FPS。

### 10.3 关键故障处理

- 单路断流：继续其他路，记录缺口；受影响区域未知，可靠重叠镜头仍可提供观察。
- 全部断流：告警并按退避策略重试；当前代码在全部流持续 30 秒无画面时失败，需新增业务恢复机制。
- 展车统计或数据库失败：不停止共享追踪任务；修复后从本模块事务进度重读日志，输出数字不重复。
- 追踪或服务器重启：新建运行标识，内存特征丢失，重新建立追踪身份；展车恢复已保存的消费进度与事件，但不自动续接重启前的人员身份，中断期间不计停留，日报标记身份断点。
- 日报生成失败或错过定时：从已保存任务状态重试或补发，不重启追踪、不重新识别访客、不丢失已发布的旧版本。
- 日志半行、磁盘满、写入失败：隔离或暂停并显式报告数据缺口，不发布正常完整性状态。
- 摄像头或展车移动：标记相关配置失效，重新标定或发布布局；生效前不输出高可信展车归属。

## 11. 安全和使用边界

上线前增加登录、角色及门店权限、HTTPS、操作审计、接口限流、上传配额和视频源白名单。管理员、运营查看者和维护人员按职责授权，导出及证据回放单独校验。

拉流能力可访问服务器内网，必须限制可配置的协议、目标主机、端口以及重定向后的目标，不开放任意地址探测。摄像头密码使用受保护的凭据存储，数据库和备份采用访问控制及适当加密。

临时 ID 不等于匿名化。视频、外观特征和可串联行为均按受保护数据处理。实际告知、使用授权、员工管理、保留期限和对外传输，由门店依据适用要求确认；本文不替代专项合规审查。上线前还应核对使用的代码、模型权重及数据相关许可。

## 12. 实施阶段与交付物

阶段按依赖推进；现场材料、人员投入和验收阈值确认后再给出日历排期。

| 阶段 | 工作内容 | 交付物与进入下一阶段的条件 |
| --- | --- | --- |
| P0：边界与现场确认 | 勘查、视频采样、角色口径、任务所有权、协议和保留需求、容量测试 | 模块边界、门店配置表、试点视频、协议草案及双方确认的验收指标 |
| P1：通用接口与独立模块 | 在追踪侧建立薄适配器和公开事件协议；建立可禁用的展车入口、独立数据目录及模拟消费者 | 不新增展车规则也能输出通用事件；原功能回归、导入边界、无模型消费和多消费者测试通过 |
| P2：空间与事件分析 | 选取少量展车和摄像头，在展车模块实现标定、消费进度、访问规则、修订与重放 | 定位误差报告、独立展车数据库及可重复计算的事件结果；未知区域被明确标记 |
| P3：每日报告闭环 | 保持特征仅内存；完善人工配置、日报 HTML/JSON、按日任务、补发、权限、告警和证据索引 | 每店每天一份逻辑报告；保存当日数据，重启身份断点和不完整时段明确展示；展车独立重启可续算 |
| P4：试运行验收 | 至少 72 小时连续运行，结合现场人工标注与故障演练 | 验收报告、参数定版、备份恢复手册、回滚与运维手册 |

迁移顺序是先固定协议与适配边界，再增加独立展车模块，最后按需逐步整理追踪内部目录。现有采集与模型入口尽量保留，不将展车规则塞进 `run_online`，不为了新模块先大规模重写整个项目。现有在线/离线播放、日志下载和停止任务行为需做回归测试。

追踪和展车维护各自的依赖、变更记录、配置及发布版本；同仓库不等于必须同步修改或同步上线。公共协议变更需要两侧共同评审，其余优化分别开发，通过契约与集成测试确认影响范围。

一期先验证“人工配置后，系统能据追踪结果判断在哪辆车附近、停留多久、是否再次返回，并保存当日完整口径的日报”。通过后再扩展追踪特征数据库与身份恢复，以及更复杂行为识别、CRM 对接、多店管理或向量数据库。

## 13. 验收标准与测试方法

以下数值为试点讨论起点，不是已测结果或交付保证。P0 必须结合空间、业务损失及硬件修订并确认。

| 项目 | 建议目标或强制口径 | 测试方法 |
| --- | --- | --- |
| 地面定位 | 有效区域检查点误差 P95 不超过 0.5 米，且足以区分相邻车辆区域 | 使用未参与拟合的检查点；按摄像头和区域分别报告，失败区域禁用精确归属 |
| 时间对齐 | 建议跨镜头对齐残差不超过 0.5 秒；未达标必须降低融合可信度 | 使用共同可见事件和源时间对比，覆盖重连和时钟跳变 |
| 访问事件 | 试点精确率目标 90%、召回率目标 85%，同时报告未知占比 | 独立人工标注有效访问，冻结规则后盲测；不能通过全部判未知刷高精确率 |
| 停留时长 | 人工有效停留至少 30 秒的匹配事件，中位绝对误差目标不超过 5 秒，同时报告 P95 | 统一遮挡和缺口口径逐事件核对，不只挑选无遮挡片段 |
| 身份连续性 | 统计错误合并、错误拆分及其对人数/时长的影响；最终阈值 P0 确认 | 同衣着、同行访客、跨镜头交接、短暂遮挡场景专项标注 |
| 增量统计 | 从帧到达服务器到结果可查，P95 目标不超过 5 秒 | 记录接收、推理、持久化、消费及发布各阶段时间，分阶段定位瓶颈 |
| 原功能独立 | 禁用展车后，原在线/离线、播放、取消和下载仍通过原回归 | 不安装展车可选依赖、不创建展车库启动原服务；检查反向导入和页面资源 |
| 展车独立 | 无模型权重或 GPU，也可消费固定日志完成业务统计；展车故障不终止追踪 | 独立运行、重放、迁移失败、数据库锁与进程退出测试 |
| 结果复用 | 同一任务只运行一份推理，两消费者各自得到完整记录 | 验证模型加载次数、独立游标、订阅退出与任务所有权 |
| 升级兼容 | 兼容的追踪升级无需改展车业务代码；不兼容协议明确报错 | 新旧事件样本、版本矩阵、升级回滚及现场业务回归 |
| 幂等与恢复 | 对同一持久化输入，重复处理或统计进程重启后，最终事件与指标不变；追踪中断另记缺口 | 注入半行、重复、乱序、事务前后退出、段切换和消费者重启 |
| 数据缺口 | 断流、超时和无法定位期间不虚增有效时长 | 注入明确长度的缺口并检查事件区间和前端质量提示 |
| 特征仅内存 | 向量不出现在数据库、文件、日志、报告或快照；追踪重启不假装恢复身份 | 用测试特征检查各输出通道；模拟追踪退出，验证新运行命名空间、报告断点和已有事件保留 |
| 人工配置 | 平面图、展车区域和摄像头标定经人工发布后生效；配置缺失时不猜测车辆 | 上传类型/尺寸、对应点不足、区域重叠、布局换位及历史生效范围测试 |
| 每日一报 | 每店每当地日期只有一份当前发布报告，包含所有正式输入对应的当日数据 | 同日多次触发、跨午夜、零目标、无数据、服务错过定时、晚到和重复补算测试 |
| 报告一致性 | HTML 与 JSON 的日期、版本和指标一致；跨日/小时区间不重复累计 | 固定事件人工核算、时间区间切分、门店总人数非展车人数求和、发布过程中退出测试 |
| 逐帧处理 | 若合同要求每帧分析，在约定输入峰值下完成输入/输出核对、无溢出丢弃且延迟达标 | 使用已知帧数输入及现场计数；源帧不可观测时不宣称端到端零丢帧 |
| 长期稳定 | 连续 72 小时无未解释崩溃；队列和有效身份容量有界；原始日志增长符合估算 | 包含营业高峰、夜间、断流、重启、磁盘告警、备份与恢复演练 |
| 访问与删除 | 未授权访问被拒绝；内存特征清理后不再参与匹配；业务备份恢复不复活应删除报告 | 权限、跨门店访问、报告明细导出、内存过期、清理和业务恢复专项测试 |

人工样本需覆盖至少一个代表性营业日中的高峰、低峰、照明变化、员工干扰、同行访客、车辆遮挡和相邻车区；以不少于 100 个可复核访问事件作为试点起点，样本不足时延长采集。调参样本与验收样本分开，记录标注规则、分歧处理和样本量。

试点结果应能追溯到日志段、规则及配置版本、证据时间段。模拟模型测试只能验证程序逻辑，不能替代现场 ReID、定位和业务准确率测试。

## 14. 启动实施前需要的材料
